Dekripsi Dokumen Konfidensial (RSA Tanpa Padding)

Target Juice Shop
Kelas Cryptography
Severity HIGH cvss 7.5
Peneliti Twist

Target: OWASP Juice Shop v6.2.0-SNAPSHOT (instance lokal — lab latihan) Endpoint: /ftp/announcement_encrypted.md + /ftp/encrypt.pyc Tanggal: 9 Oktober 2026 Peneliti: Twist Severity: HIGH (Sensitive Data Exposure / Cryptographic Issues)

1. Ringkasan

File /ftp/encrypt.pyc berisi skrip enkripsi yang membocorkan algoritma + kunci publik RSA yang dipakai untuk melindungi announcement_encrypted.md.

Karena enkripsi dilakukan tanpa padding dan setiap karakter dienkripsi terpisah (m selalu < 256), penyerang bisa brute-force 256 kandidat per karakter — tidak perlu memfaktorkan modulus RSA yang 1024-bit.

Hasil: seluruh 1.194 karakter dokumen konfidensial berhasil didekripsi (0 gagal).

2. Dampak

Aspek Detail
Autentikasi Tidak butuh — file di direktori publik /ftp
Kendala kriptografi NOL — tidak perlu faktorisasi RSA
Waktu serangan < 1 detik untuk 1.194 karakter
Data terungkap Dokumen konfidensial "Major Announcement — Token Sale / ICO"

Prinsip yang dilanggar: prinsip Kerckhoffs — keamanan harus bergantung pada kunci privat, bukan pada kerahasiaan algoritma. Di sini algoritmanya bocor (encrypt.pyc), skema enkripsinya cacat, dan hasilnya = dokumen terbuka.

Bukti 3 — Identifikasi kelemahan

Range nilai        : semua < N (1024-bit)

Kelemahan kritis:
  plaintext = ord(char) → selalu < 256
  → ruang pencarian cuma 256 kemungkinan per karakter
  → brute-force = 256 eksponensiasi modular

Catatan — Jebakan yang Ditemukan

GitHub issue Juice Shop #1392 melaporkan bahwa nilai N di dalam .pyc berbeda dari N yang dipakai untuk mengenkripsi file. Artinya:

✗ Faktorisasi N       → sia-sia (N tidak sesuai / tidak bisa difaktorkan)
✗ Menghitung d        → tidak mungkin tanpa p, q
✅ BRUTE FORCE 256    → JALAN, karena tidak butuh N yang benar untuk
                        SEMUA kandidat — cukup cari m yang menghasilkan c

Pelajaran: selalu serang kelemahan skema, bukan kelemahan kunci. 1024-bit RSA itu kuat — tapi RSA tanpa padding untuk pesan 1 byte tidak.

4. Akar Masalah

Tiga kesalahan berlapis:

1. Skrip enkripsi disimpan di direktori publik encrypt.pyc ada di /ftp — menyerahkan algoritma ke penyerang (langgar Kerckhoffs).

2. RSA tanpa padding (textbook RSA)

# SALAH — textbook RSA
encrypted_document.write(str(pow(ord(char), e, N)) + '\n')

# BENAR — pakai OAEP padding + enkripsi per-blok
from Crypto.Cipher import PKCS1_OAEP
cipher = PKCS1_OAEP.new(public_key)
encrypted = cipher.encrypt(data)   # pesan utuh, bukan per karakter

3. Enkripsi per karakter Membuat ruang pencarian jadi 256. Bahkan dengan padding, mengenkripsi per karakter itu pola yang buruk.

5. Saran Perbaikan

1. Hapus skrip enkripsi dari direktori publik

# encrypt.pyc TIDAK BOLEH ada di /ftp — pindah ke luar document root

2. Ganti ke RSA dengan OAEP + enkripsi per-blok

from Crypto.PublicKey import RSA
from Crypto.Cipher import PKCS1_OAEP

key = RSA.import_key(open('private.pem').read())
cipher = PKCS1_OAEP.new(key)
with open('announcement.md','rb') as f:
    data = f.read()
ct = cipher.encrypt(data)          # enkripsi utuh, ada padding

3. Jangan pakai RSA untuk data besar RSA cuma untuk enkripsi kunci. Untuk file pakai hybrid:

# RSA untuk membungkus kunci AES, AES untuk file
aes_key = os.urandom(32)
ct_file = AESGCM(aes_key).encrypt(nonce, data, None)
ct_key  = PKCS1_OAEP.new(rsa_pub).encrypt(aes_key)

4. Matikan directory listing serve-index di /ftp Lihat 002-juice-shop-full-recon.md §2.

5. Audit ulang berkas di direktori publik Hapus/relokasi semua .bak, .pyc, .kdbx, .yml, .json dari sana.
